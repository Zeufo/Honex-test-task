# Мини-парсер объявлений Avito по артикулам

Ищет каждый артикул из `config.py` на Avito, отбирает объявления в новом
состоянии из Москвы и Московской области, сортирует по возрастанию цены
и сохраняет 5 самых дешёвых (или все, если найдено меньше 5) в `result.csv`
и `result.xlsx`.

## Запуск

```bash
pip install -r requirements.txt
cd src
python3 main.py
```

Результат появится в `result.csv` и `result.xlsx` в корне проекта (на уровень выше `src/`) - независимо от того, откуда именно запущен `main.py`, пути считаются от расположения `config.py`.

## Как задаются регион, состояние и сортировка

Всё в одном месте — `config.py`:

- **Регион** — часть пути в `BASE_URL`: `https://www.avito.ru/moskva_i_mo`
  (Москва и МО). Дополнительно каждое объявление перепроверяется в
  `run.py::_passes_filters()` по подстроке `"моск"` в поле города/адреса —
  чтобы не полагаться только на фильтр самого сайта.
- **Состояние "только новое"** — параметр запроса `condition=new` в
  `SEARCH_PARAMS`. Дополнительно перепроверяется на своей стороне по
  подстроке `"нов"` в поле состояния карточки.
- **Сортировка по цене** — параметр `s=104` в `SEARCH_PARAMS` (подсказка
  Avito сортировать "сначала дешевле"), но финальная сортировка и выбор
  топ-5 в любом случае выполняются в коде (`run.py`), на сам сайт в этой
  части не полагаемся.

## Как устроен фолбэк, если Avito блокирует запрос

Прямой запрос к Avito ведёт себя нестабильно: в одних попытках возвращается
HTTP 429 (too many requests), в других — HTTP 200, но тело ответа на деле
страница капчи/блокировки (~28 КБ, маркеры "captcha", "Доступ ограничен",
карточек `data-marker="item"` — 0). В обоих случаях реальной выдачи нет.
Обход блокировок в задание не входит и по условиям ТЗ не считается
недостатком решения — поэтому пайплайн устроен так:

1. `fetcher.py::AvitoFetcher.fetch()` пробует live-запрос. Если статус не
   200 (например 429), либо статус 200, но тело похоже на страницу
   капчи/блокировки (проверяется по ключевым словам в тексте, так как Avito
   иногда отдаёт капчу с кодом 200) — возвращает `None`. В обоих случаях в
   лог пишутся статус, размер тела и найденные маркеры блокировки.
2. `run.py` в этом случае переключается на `loader.py::CacheLoader`, который
   читает заранее подготовленный тестовый HTML из `cache/<артикул>.html`.
3. Дальше пайплайн — парсинг, фильтрация, дедуп, сортировка, экспорт —
   одинаковый и для live-ответа, и для тестового HTML.

Если нет ни live-ответа, ни тестового HTML-файла для артикула — в
результат попадает строка со статусом `ошибка`. Если страница получена, но
подходящих объявлений не найдено — строка со статусом `не найдено`.

## Структура кода

```
honex_parser/
├── src/
│   ├── config.py        — артикулы, URL, параметры поиска, константы
│   ├── fetcher.py        — live-запрос к Avito, ретраи, детекция блокировки
│   ├── loader.py          — чтение локального HTML из cache/ (фолбэк)
│   ├── parser.py           — разбор HTML в список объявлений
│   ├── run.py                — оркестрация: фильтры, дедуп, сортировка, топ-5
│   ├── exporter.py            — экспорт в CSV/XLSX
│   ├── main.py                 — точка входа
│   └── logger_config.py
├── cache/
│   ├── 223112R020.html   — тестовый HTML (эмулирует выдачу Avito)
│   └── 233002F700.html
├── result.csv / result.xlsx   — появляются после запуска, в корне проекта
├── requirements.txt
└── README.md
```

`cache/` лежит на одном уровне с `src/` — путь до неё вычисляется в
`config.py` через `Path(__file__).resolve().parent.parent / "cache"`, так
что запуск работает одинаково что из корня проекта, что из `src/`.
